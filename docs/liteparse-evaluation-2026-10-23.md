# LiteParse evaluation — 2026-10-23

## Decision

Keep LiteParse as an evaluation candidate. Its OCR-disabled output does not
justify replacing mdaddict's PDF backend or adding a production extra yet.
It reconstructs the simple table and is fast on prepared inputs, but leaves the
structured-math gap and introduces two content-check regressions relative to
mdaddict PDFium. Retain the compatibility backend for existing math/layout work.

Prefer a dedicated table library's public API for the next bounded experiment.
LiteParse's substantial Rust table pipeline is not a small module to copy.
No runtime dependency, default selection, source contract, hold policy, or gold
changed in this evaluation. Model-enabled OCR remains a separate evaluation.

## Method

Windows x64, Python 3.13.7, isolated `liteparse==2.17.0` environment. The wheel
was published on 2026-10-22. LlamaParse's hosted service was not used.

Reuse the [existing corpus](pdf-corpus-2026-10-23.md): 16 originals, 29 distinct
reviewed pages, 18 source jobs, and 54 automatic content checks. Seventeen
reviewed pages are real-source material and twelve are invented controls.
One additional inherited-form page is processed but unreviewed: each pass
processes 30 pages. This difficult sample does not estimate population accuracy.

The candidate received the exact prepared files used in the prior PDFium run,
including unchanged original form documents. Earlier non-form subsetting used
PyMuPDF; this is a conversion comparison, not a PyMuPDF-free preparation harness.
Original, manifest, imported-gold, prepared-input, evaluator, runner, native-file,
and report hashes are retained locally. Originals/gold stayed unchanged.
Re-scoring both prior backends reproduced all 108 prior content verdicts.

One configuration was fixed before parsing: Markdown output, OCR off,
headers/footers retained, stored-form extraction and form rendering enabled,
layout blocks/complexity diagnostics enabled, image placeholders, image byte
extraction off. Other options retain library defaults. This is a preservation
profile, not an unconfigured-default benchmark; no post-result tuning occurred.
Score each page's native `markdown` with the existing checker. No spatial-text
fallback, synthesized tables/equations/form summaries, or new accepted
renderings. Evaluation page identities do not implement production source spans.

## Content results

Counts match selected existing targets, not general accuracy.

| Check kind | LiteParse | mdaddict PDFium | Compatibility |
|---|---:|---:|---:|
| Text | 16/17 | 17/17 | 15/17 |
| Reading order | 3/4 | 4/4 | 3/4 |
| Coverage | 6/6 | 5/6 | 5/6 |
| Structured equations | 0/21 | 0/21 | 15/21 |
| Tables | 1/4 | 0/4 | 3/4 |
| Matrices | 0/2 | 0/2 | 2/2 |
| **All content** | **26/54** | **26/54** | **43/54** |

LiteParse matches 13/40 real-source targets and 13/14 control targets; PDFium
matches 14/40 and 12/14. Two improvements are correlated: the simple table passes
both its grid and whole-content check. The two regressions are QML page 6's
column reading order and the stale form's stored value. Native form metadata
correctly reports `Specimen 99`, while Markdown emits the old appearance
`Specimen 42`. Field extraction/rendering did not reconcile them. Checkbox/radio
states are also retained in metadata without appearing in candidate Markdown.

Wong's truth-table columns collapse into combined cells; its oracle table and
matrix relationships are not recovered. Demsar needs a narrower interpretation:
its nine target numbers appear in a 3-by-3 subsection of a larger table, which
the current exact-grid check rejects. This does not show all nine numbers were
lost; surrounding row-label fidelity is a separate question. Equation mismatches
likewise mean required structured representations did not match, not that every
mathematical character disappeared. No comparator or gold was relaxed.

Of the seventeen formerly manual checks, sixteen remain pending and the code
check has missing required lines. None is approved. Six quarantine sentinels
are **not evaluated**: the raw candidate has no mdaddict issue/publication
adapter. Hold counts, false-hold rates, publication safety, and cache integration
are unmeasured, rather than zero. `needs_ocr` is false on six pages with equation
mismatches, so it cannot serve as fidelity clearance.

All 18 source-job repeat parses were stable after canonical serialization of
returned data. These are fresh parses, not cache hits. No page errors occurred;
none of the 1,752 returned text items carried OCR confidence.

## Footprint and timing

The hash-verified Windows wheel is 12,148,209 bytes (12.15 MB). Recorded installed
files total 27,880,452 bytes (27.88 MB), excluding generated bytecode and Python.
This includes a 20,226,048-byte extension and 7,107,072-byte PDFium DLL. No required
Python distribution dependencies are declared. The bundled CycloneDX inventory
lists 347 components, not 347 separately installed Python packages; its scope
can include build/target components and does not establish runtime linkage.

Existing recorded profiles total about 24.28 MB for mdaddict PDF and 66.78 MB for
compatibility. These include metadata but exclude generated bytecode and
mdaddict's editable source bytes. They are approximate footprint context, not
clean-install closure or incremental disk allocation. Adding LiteParse alongside
the current PDF stack retains two PDFium bindings/binaries.

Three serial uncached passes through the same 18 prepared jobs produced these
median corpus times: raw LiteParse **147 ms**, mdaddict PDFium **236 ms**, and
mdaddict compatibility **6,004 ms**. Results were stable across timed repeats.
The workloads differ: mdaddict also performs fingerprinting, normalization,
source contracts, form handling, and capability guards. Files were already
subset and warm. Import/startup, subsetting, report serialization, and separate
output validation were outside timed calls. This is a small-corpus latency
observation, not an equal-work engine ranking or a whole-book throughput/RAM claim.

## Install or copy

Inspected source: tag `python-v2.17.0`, commit
`a47f56d1aff38a4525ea9402c91f7457e5ab4ba3`. The top-level license is Apache 2.0.
Bundled native-component notices/linkage still need release review. The inventory
includes MPL-2.0 entries; the top-level license alone does not establish a fully
permissive dependency closure.

The table module has 7,724 lines, with tests beginning at line 5,803. Operational
code depends on projected lines, text/word geometry, graphics, layout-block
types, whitespace processing, and font classification. A broad copy would
require a substantial port and adaptation. If later corpus evidence favors
LiteParse, use its maintained Python interface as an optional backend first.
A smaller copied helper still needs a demonstrated benefit, bounded interface,
provenance/license/notices, and independent regressions.

Primary references: [Python interface](https://github.com/run-llama/liteparse/blob/a47f56d1aff38a4525ea9402c91f7457e5ab4ba3/packages/python/README.md),
[table source](https://github.com/run-llama/liteparse/blob/a47f56d1aff38a4525ea9402c91f7457e5ab4ba3/crates/liteparse/src/markdown_layout/tables.rs),
[release license](https://github.com/run-llama/liteparse/blob/a47f56d1aff38a4525ea9402c91f7457e5ab4ba3/LICENSE).

## Local evidence and reproduction

Private evidence remains in `education/engine/out/liteparse-2026-10-23/`:
`prepared.json`, `native.json`, `comparison.json`, `diagnostics.json`,
`footprint.json`, the verified wheel, pinned source files, and `timing-*.json`.
Raw real-source text is not copied into this repository. From the application:

```powershell
uv venv --python engine/.venv/Scripts/python.exe engine/out/liteparse-2026-10-23/.venv
uv pip install --python engine/out/liteparse-2026-10-23/.venv/Scripts/python.exe liteparse==2.17.0
engine/.venv/Scripts/python.exe -X utf8 engine/out/liteparse-2026-10-23/run.py
engine/.venv/Scripts/python.exe -X utf8 engine/out/liteparse-2026-10-23/timing.py
```

Downloads were explicit evaluation preparation. Python socket connections were
disabled during parsing; this is not an OS-level block on Rust sockets. OCR was
explicitly off with no OCR server or AI provider configured. No OCR, model
inference, hosted parsing, publication, staging, or commit occurred.
